# hand-flying 모드

자동조종(에이전트가 파일 직접 수정) 대신 수동비행. 에이전트는 코드를 **게시**하고,
사용자는 **직접 타이핑**하거나, 뷰어의 "AI가 작성" 버튼으로 그 블록의 작성을 에이전트에게 맡긴다.

## 절대 규칙

- 이 모드에서는 프로젝트 파일을 Edit/Write/sed 로 **직접 수정하지 않는다.** 코드는 `hf post` 로만 내보낸다.
  파일과 뷰어가 어긋나면 이 모드의 의미가 사라진다.
  예외는 하나 — 사용자가 "AI가 작성" 으로 맡긴 블록(`[ai-write]` 이벤트)만 에이전트가 반영한다.
- 파일 읽기는 자유. `before` 펜스는 현재 파일 내용을 **글자 그대로** 옮긴다.
- 뷰어는 코드 가시성 도구다. 목적은 코드 추적, 구현 범위의 큰 그림, 현재 작업 흐름 추적 세 가지뿐이다.
  뷰어에는 대화 기능이 없다. 수정 요청에는 **코드와 블록 설명으로만** 답한다(풀어 말할 것이 있으면 블록의 설명을 고친다).

## 시작

1. `hf` 가 PATH 에 없으면 hand-flying 저장소에서 `npm link` 를 안내한다(또는 `node <저장소>/bin/hf.mjs`).
2. `hf start` 로 뷰어를 백그라운드에서 띄운다. 이미 실행 중이면 주소만 출력하고 끝난다. 종료는 `hf stop`.
3. 사용자에게 `http://127.0.0.1:4100` 을 안내한다.

## 게시 — `hf post`

프로젝트 폴더에서 heredoc 으로 넘긴다. 브랜치(사이드바 대분류)는 기본이 현재 git 브랜치, 다르게 묶으려면 `--branch 이름`.

````bash
hf post <<'EOF'
# 커밋 제목 (사이드바 소분류 = 한 단계)
### 맥락
이 작업이 왜 필요한가. 지금 무엇이 문제이고 어떤 배경에서 나왔는지.
### 목적
이 단계가 끝나면 무엇이 가능해지는가. 다음 단계와의 연결.
### 순서
1. UserService 에 Repository 의존성 추가 (생성자)
2. findById 에서 없는 사용자 예외 처리
3. 테스트로 예외 경로 확인

## src/main/java/com/acme/UserService.java#method findById
`findById` 가 없는 사용자에게 null 대신 `UserNotFound` 예외를 던지도록 바꾼다. 지금은 null 을 돌려줘서 호출부가 사용자가 없는 경우와 조회 실패를 구분하지 못한다.

```java before
    public User findById(long id) {
        return null;
    }
```

```java
    public User findById(long id) {
        return repository.findById(id)
            .orElseThrow(() -> new UserNotFound(id));
    }
```
EOF
````

형식:

- `# 제목` 한 줄, 그 아래 요약을 `### 소제목` 절로 쓴다. 요약에 `## ` 제목은 쓰지 않는다(`## ` 는 블록 시작 예약어).
- **`### 맥락`, `### 목적` 은 필수**(없으면 게시가 거부된다). 맥락 = 왜 필요한가, 목적 = 끝나면 무엇이 되는가.
- 블록이 2개 이상이면 `### 순서` 를 번호 목록(`1. …`)으로 쓴다. 뷰어가 별도 상자로 보여준다.
  항목은 블록 순서와 맞추고, 한 항목에 한 가지 일만 쓴다.
  **항목마다 대상 블록의 파일명(확장자 없이, 예: `UserService`)이나 블록 이름을 넣는다.** 뷰어는 그 이름으로
  항목과 블록을 이어, 항목을 누르면 해당 블록으로 이동시킨다.
- `## 파일경로#종류 [이름]` — 경로는 프로젝트 루트 기준. **종류는 필수**이고 아래 고정 범주 중 하나만 쓴다
  (범주 밖이면 게시 거부). 이름(메서드명·키 이름 등)은 선택이다. 화면에는 범주만 보이고, 이름은 순서 항목과 블록을 잇는 데 쓰인다.

  | 종류 | 단위 |
  | --- | --- |
  | `imports` | import·include·require·use 묶음 |
  | `field` | 필드·속성·상수·전역 변수 선언 |
  | `constructor` | 생성자·초기화 함수(`__init__` 등) |
  | `method` | 메서드·함수 |
  | `type` | class·interface·enum·record·struct 선언 전체 |
  | `test` | 테스트 케이스·픽스처 |
  | `block` | 메서드 안 일부 등 그 밖의 코드 조각 |
  | `query` | SQL 문·DDL |
  | `key` | 설정 키·섹션 (yaml·properties·json·toml·xml·env) |
  | `section` | 문서의 절 (md·txt·adoc) |
  | `file` | 파일 전체 (새 파일·전체 교체) |

  예: `#method afterMessageHandled`, `#constructor`, `#key spring.datasource`, `#file`.
- `before` 펜스 = 수정할 원본 구간. 파일에서 **정확히 한 번** 나와야 한다. 아니면 게시가 거부되니 구간을 넓혀 다시 게시.
- `before` 생략 = 파일이 없으면 새 파일, 있으면 파일 전체 교체.
- 코드에 ```` ``` ```` 가 들어 있으면 바깥 펜스를 백틱 4개로 늘린다.
- 마크다운 블록은 `hf post` 가 앞뒤 줄을 붙여 빈 줄로 나뉜 덩어리(문단·표·목록)와 코드 펜스 전체까지 넓힌다. 뷰어 Preview 가 그려지게 하려는 것이므로, 표는 머리 행부터 담아 게시하는 편이 낫다.
- 펜스에는 **코드 언어 id** 를 쓴다(예: ```` ```java ````). 블록 메타데이터에 기록되어 뷰어 하이라이트에 그대로 쓰인다.
  생략하면 확장자로 정하고(모르는 확장자는 text), 목록 밖 이름이면 게시가 거부된다.
  지원: `java` `kotlin` `groovy` `scala` `c` `cpp` `csharp` `go` `rust` `python` `ruby` `php` `swift` `javascript` `typescript` `jsx` `tsx` `html` `css` `scss` `vue` `json` `yaml` `toml` `ini` `properties` `xml` `sql` `bash` `dockerfile` `markdown` `diff` `text` (별칭 js·ts·py·sh·yml·kt·c++ 등 허용)
- 줄 번호는 CLI 가 실제 파일에서 계산한다. 쓰지 않는다.
- `## ` 줄 아래부터 펜스 전까지는 블록 **설명**이다. 뷰어가 "Explain" 라벨을 붙이므로 "설명:"·"근거:" 를 앞에 쓰지 않는다.
  쓰는 법은 아래 "문장 작성" 을 따른다.

## 문장 작성 — 설명·맥락·목적

블록 설명(Explain)과 요약의 `### 맥락`·`### 목적` 에 모두 적용한다.

- 첫 문장에서 무엇을 바꾸는지와 왜 바꾸는지 밝힌다.
- 설명은 **현재 상태 → 충돌하는 요구사항 → 변경 내용 → 영향 범위 → 다음 작업** 순서로 쓴다.
- 한 문장에 타입 목록, 필드별 예외, 원인, 결론을 모두 넣지 않는다. 독자가 관계를 다시 추적해야 하면 문장을 나눈다.
- "새 메시지 셋", "공통 계약을 줄인다" 같은 추상적인 표현 대신 구체적인 타입과 제거할 필드를 적는다.
- 변경 대상이 인터페이스인지 구현 레코드인지 구분한다. 유지되는 필드도 어느 쪽의 필드인지 밝힌다.
- "동작은 바뀌지 않는다", "수정할 필요가 없다" 는 결론에는 바로 뒤에 근거를 붙인다.
- 이슈 번호와 다음 작업은 본문의 기술 설명에서 분리해 마지막에 짧게 적는다.
- 코드 식별자는 원래 이름을 유지하되, 그 사이를 잇는 한국어는 자연스러운 문장으로 쓴다.
  `방향으로 줄인다`, `그대로 넣을 수 없다` 처럼 뜻을 되짚게 하는 표현은 피한다.
- 식별자는 `백틱` 으로 감싼다. 뷰어가 코드 글꼴로 보여 준다.

## 블록 크기

- 상한: Java 등 클래스 기반 언어는 클래스 하나, C·Python·설정 파일 등은 파일 하나.
- 작은 수정: 의미가 통하는 최소 단위 — 메서드, 함수, 제어 블록, YAML 키.
- 한 커밋 = 사용자가 한 번에 따라 칠 수 있는 한 단계. 블록 1~5개를 권장.
- 다음 단계가 이전 단계 코드를 고치면, 이전 단계가 파일에 반영되기 전엔 `before` 를 찾을 수 없다.
  → 이전 커밋이 `완료 n/n` 이 될 때까지 기다렸다가 게시한다.

## 수정 — `hf post --amend <커밋id>`

수정 요청은 새 단계를 만들지 않는다. 요청이 달린 커밋의 내용을 수정본으로 **통째로 교체**한다.
게시 형식은 `hf post` 와 같다(제목·요약·블록 전체를 다시 보낸다). 코드가 그대로인 블록은 완료 상태가 유지된다.

- `before` 는 지금 파일 기준으로 다시 잡는다. 사용자가 이전 안을 이미 반영했으면 그 반영된 코드가 `before` 다.
- "왜 이렇게 했어?" 같은 질문도 답글이 아니라 해당 블록의 설명을 보강해 amend 한다.

## 이벤트 루프 — `hf wait`

게시 후 `hf wait` 을 **백그라운드로** 실행한다(기본 600초, 이벤트가 오면 즉시 종료).
끝나면 출력을 처리하고 다시 `hf wait`.

| 출력 | 의미 | 대응 |
| --- | --- | --- |
| `[request] commit=<id>` | 수정 요청 | 그 커밋을 `hf post --amend <id>` 로 교체. 터미널에도 뷰어에도 답글은 쓰지 않는다 |
| `[request] commit=<id> blocks=<b…>` | 사용자가 화면에서 코드 블록을 선택해 보낸 수정 요청 | 요청은 "대상 블록" 에 적힌 그 코드에 대한 것. 그 블록을 중심으로 고쳐 `hf post --amend <id>` |
| `[done] … (완료 n/n)` | 블록 완료 체크 | 커밋 전체가 완료되면 다음 단계 게시 |
| `[ai-write] commit=<id> blocks=<b…>` | 사용자가 블록 작성을 맡김 — "AI 작성"(1개) 또는 "AI 전체 구현"(남은 블록 전부). 뷰어에 AI Writing | `hf apply <id> <b…>` 로 반영 → 필요하면 컴파일·테스트 확인 → `hf done <id> <b…>`. done 을 보내야 뷰어가 Done 으로 바뀐다. apply 가 실패하면(원본 구간 불일치) Edit 로 블록과 같은 결과를 만든 뒤 done. 같은 파일 블록은 출력 순서대로 반영한다 |
| `[undone]` | 완료 해제 | 대기 |
| 시간 초과 | 이벤트 없음 | 바로 다시 `hf wait` (백그라운드) |

## 연결 상태와 대기 재개

- `hf wait` 은 도는 동안 심장박동을 남긴다. 뷰어 왼쪽 아래에 **에이전트 대기 중 / 작업 중 / 연결 끊김** 이 보이고,
  끊겨 있으면 "AI 작성"·"AI 전체 구현" 버튼이 막힌다.
  → hand-flying 모드에서는 이벤트를 처리하는 동안을 빼고 **항상 `hf wait` 이 백그라운드에서 돌고 있어야** 한다.
- 이벤트를 받은 뒤 15분 안에 다시 `hf wait` 하지 않거나, wait 프로세스가 죽으면 끊김으로 표시된다.
- 사용자가 **"/hand-flying 대기 재개"**(또는 "대기 재개", "다시 붙어")라고 하면:
  1. `hf start` — 뷰어가 꺼져 있으면 켠다.
  2. `hf wait --timeout 0` — 끊겨 있던 동안 쌓인 이벤트를 바로 받아 위 표대로 처리한다.
  3. `hf wait` 을 백그라운드로 다시 띄우고, 뷰어에 "에이전트 대기 중" 이 보인다고 한 줄로 알린다.
